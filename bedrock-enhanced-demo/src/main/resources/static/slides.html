Bedrock Enhanced Client

A High-Level Client for Stateful Conversation Management
AWS SDK for Java v2  ·  services-custom/bedrock-enhanced
Presented By: Abhinav Goyal

The Problem: Building Multi-Turn Conversations is Hard

  • No conversation state — The Converse API is stateless. Developers must manually track and resend full message history every turn.
  • Unbounded cost growth — Each turn re-sends all previous messages as input tokens. A 20-turn conversation costs 20x more per turn than the first.
  • Context window limits — Models have finite context windows. Without management, long conversations fail with validation errors.
  • No built-in caching — Prompt caching exists but is not enabled by default. Different models have different caching mechanisms and constraints.
  • Model-specific complexity — Each model family has different context limits, caching strategies, and summarization behaviors. Developers must handle each one differently.
  • Retry is insufficient — Standard SDK retry strategies use generic exponential backoff. Bedrock needs model-aware throttling — token-per-minute limits, concurrent request caps, and adaptive backoff that responds to real-time capacity signals.

The Solution: BedrockEnhancedClient

A high-level wrapper around BedrockRuntimeClient that manages the full lifecycle of multi-turn conversations — abstracting away model-specific differences so developers write 3 lines of code instead of 50.

// Create client once, reuse across sessions BedrockEnhancedClient client = BedrockEnhancedClient.builder() .contextWindowConfig(c -> c.maxTokens(8192) .trimStrategy(TrimStrategy.COST_OPTIMIZED)) .promptCachingConfig(p -> p.enabled(true)) .build(); // Create a session, start talking ChatSession session = client.createSession("us.anthropic.claude-sonnet-4-5"); ChatResponse resp = session.converse("Tell me about Horcruxes"); ChatResponse followUp = session.converse("How were they destroyed?");

Features at a Glance

Context Window Management

  • 5 trim strategies — Sliding window, summarize, chunked, cost-optimized, drop-oldest
  • Token-based limits — Uses actual Bedrock response counts, no heuristics
  • Time-based expiry — Auto-expire messages older than a duration
  • Overflow policies — Auto-trim or reject (caller decides)

Cost & Performance

  • Automatic prompt caching — Inserts CachePointBlock markers transparently
  • Real-time cost tracking — Per-session CostEstimate with cache savings
  • Token budget enforcement — Hard cap on total session spend
  • Client-side rate limiting — Token bucket to avoid throttling

Reliability

  • Model-aware throttling — Goes beyond standard retries with token-per-minute tracking and adaptive backoff based on real-time capacity signals
  • Bedrock-specific retries — Separate policies for throttling (429) vs transient errors (5xx) with full-jitter backoff

Developer Experience

  • Model-agnostic API — Hides per-model differences in caching, context limits, and summarization behind a single interface
  • Familiar pattern — Same module style as other SDK enhanced clients and high-level libraries

Context Window Management Strategies

When the context window cap is reached, the enhanced client automatically applies one of these strategies:

Strategy Behavior Trade-off
SLIDING_WINDOW Drops oldest user/assistant pairs Simple, loses old context
SUMMARIZE Calls model to summarize older messages Preserves semantics, extra API call
CHUNKED Keeps most recent N chunks of M messages Predictable boundaries
COST_OPTIMIZED Coordinates trimming with prompt caching Lowest cost per turn, uses cache
DROP_OLDEST_KEEP_LAST Keeps only the latest message Aggressive reset, stateless Q&A

Deep Dive: COST_OPTIMIZED Strategy Recommended

The smartest strategy — coordinates context trimming with Bedrock's prompt caching to minimize the average cost per turn.

  • Automatic cache checkpoints — Inserts CachePointBlock after the last assistant message each turn. The conversation prefix becomes cacheable.
  • Cache-read pricing — Subsequent turns pay ~10% of normal input rate for cached prefix tokens (e.g., $0.30/MTok vs $3.00/MTok for Sonnet).
  • Bulk trimming — When uncached tokens exceed a threshold, trims down to half capacity and freezes remaining turns as a cacheable prefix.
  • Zero code changes — Just set trimStrategy(COST_OPTIMIZED) and promptCaching(enabled: true). Everything else is automatic.
